## 在现有发布中接入

1. 在已应用 [001 基础迁移](../../migrations/mysql/001_managed_task.sql) 的数据库中依次补齐 [002 能力监控](../../migrations/mysql/002_capability_monitoring.sql) 和 [003 运行轨迹](../../migrations/mysql/003_run_trace.sql)，再启动新版 API 和 worker。沿用 [M1 部署说明](m1-managed-support.md) 中的数据库变量、凭证文件、模型密钥和项目授权。升级会生成新的发布 ID，保留已有任务对应的旧版 worker，直到它们处理完毕。
2. 复制[含 Skill 和 Tool 的完整发布示例](../../examples/m1/release-capabilities.json)，填入实际 HTTPS 模型端点、模型标识、窗口和价格。将两个进程的 `AGENTOS_RELEASE_FILE` 指向这份文件。运行 `agentos capabilities` 检查部署清单元数据，用 `agentos release-id` 获取提交任务所需的发布版本。
3. 新 Skill 用 `kind=skill` 声明名称、版本、负责人、来源、许可证和文本，通过 `requires` 精确绑定依赖工具的名称与版本。该文本以带来源的用户消息数据进入上下文，和模型窗口预算一起检查。一个已发布名称和版本固定其摘要，修改文本或依赖须发布新版本。
4. 示例 Tool 用 `kind=tool`、`implementation=lexical_search/1` 选择已有的本地适配器，`limit` 约束返回数量。worker 先从 MySQL 取得当前主体有权读取的文档，再把候选资料交给工具；工具只对内存中的候选做检索。默认发布继续使用原有的内置检索。任何新的工具实现都需要增加适配器和契约测试；在 JSON 中填写 URL、shell 命令或 Python 导入路径无法创建可执行工具。
5. 提交常规 `POST /v1/tasks`，客户端指定已登记的发布版本。运行时按固定清单使用能力。服务端复核当前权限、证据版本、租约和根预算后才允许模型发送。外部模型返回的 `tool_calls` 当前仍会被拒绝。

接入另一个同契约的本地证据工具时，实现 `fn(query, candidates, limit)`，从传入的已授权候选中返回包含 `source_id/version/location/score` 的坐标列表。在[可信工具适配表](../../src/agentos/gateways/tool/registry.py)的 `EVIDENCE_TOOLS` 中把固定 implementation ID 绑定到执行函数及其依赖源码路径，再在发布清单引用这个 ID。公共网关校验参数、返回结构、来源坐标、数量和字节上限，worker 的上下文和监控路径可直接复用。此只读 Profile 每轮支持一个检索 Tool，可加载多个文本 Skill。

后续接入诸如订单查询或退款的外部工具时，按文档先登记输入/输出原始 Schema、凭证引用、目的地、费用和副作用，再实现 Tool Gateway 的执行与结算。读取订单须在目标系统实施资源授权；退款等写入还需参数绑定审批、幂等键和未知结果核对。两类外部调用均应各自保留操作 ID、尝试与回执，给监控提供真实执行数据。当前模型发送表约束每任务一次 dispatch，接入多步工具调用前需扩展此数据模型。

## 查看监控

启动 API 后打开 `/monitor`，输入项目 ID 和 Bearer 凭证，载入后可按任务查看时间线，也可按 Agent 发布版本查看[一次运行的轨迹](agent-run-trace.md)。监控页面从同源 API 读取数据。凭证保留在页面内存，服务端按凭证授予范围和 MySQL 当前项目成员关系处理每次查询。

| 入口 | 数据与范围 |
| --- | --- |
| `GET /v1/projects/{project_id}/resources` | 资源管理页 `/resources` 的数据源。校验凭证和实时成员关系后，返回当前活动发布的 `agent_version_id`、`counts.skill`、`counts.tool`，以及每项的类型、名称、版本和摘要。数量与时间窗口和运行次数无关。 |
| `GET /v1/projects/{project_id}/monitoring?hours=24&limit=50` | 按任务创建时间选取 1～168 小时的样本，最近任务列表 1～200 条。汇总任务状态、模型准入、待核对、已结算/预留费用和已知 Token 用量，以及按能力版本汇总的执行状态和耗时。活动发布的能力清单独立列出。 |
| `GET /v1/tasks/{task_id}/timeline` | 读取任务事件、上下文准备、Skill 加载、Tool 执行和模型准入/回执的元数据。子能力关联对应的上下文准备，快照可关联最终被准入的模型输入。 |
| `GET /v1/context-snapshots/{snapshot_id}` | 任务所有者按当前授权、来源状态和留存策略检查快照。项目监控凭证本身不会授予读取他人回答、输入或快照正文的权限。 |

普通凭证只查看本人在已授权项目中的任务。若运维人员确需监控一个项目的所有任务，在其已有的凭证记录内显式加入 `"monitor_project_ids": ["support"]`，项目同时须属于该凭证的 `project_ids`。按现有认证机制重启 API 加载配置；撤销 MySQL 项目成员资格对后续查询同步生效。

给控制台单独发放令牌时，将其 SHA-256 摘要和身份记录加入凭证配置顶层的 `monitor_credentials` 数组。字段与 `credentials` 相同，数组间的摘要须唯一，身份需要有效的项目成员关系。此类令牌在公网网关和私有 API 都只允许监控元数据查询。任务提交、取消、输入或回答详情、快照正文均返回 403。部署端原子替换凭证文件后应重建 API，重新挂载并加载配置。明文令牌通过私有渠道交付。

解释指标时区分三种情况：

- 目录中的能力可能一次都没运行。调用次数与失败率以实际调用记录为依据。新版 worker 会记录上下文准备，未启用 Skill/Tool 的发布可继续使用原路径。旧 worker 的任务只有原有任务/账务记录，历史缺失的能力耗时无法回填。
- 成功组装快照、成功完成本地能力调用、提交发送准入，以及收到可核对的模型回执，是不同阶段。进程崩溃可能只留下开始记录；已经准入且缺少回执的请求保持待核对，不能推断实际发送次数或把未知费用算作零。
- 账本使用人民币微元，100 万微元等于 1 元。Token 只汇总有计量回执的部分。项目聚合以任务或发送记录单独统计费用；一个任务中的多次能力调用不重复累计同一笔模型费用。能力耗时是本地执行跨度，存在父子嵌套，不能将各行时长相加为端到端耗时。
- 同一能力版本的 P95 取已结束调用耗时升序的第 `ceil(0.95 × N)` 个样本，包含失败调用。未结束的调用单列。每次项目查询最多列出 200 组能力，每个任务最多返回最近 500 条时间线事件；响应会标记截断。

统一测试阶段可执行 `python -m pytest tests/contracts`。可选浏览器用例依赖 Playwright 和 Chromium，预先安装可用 `python -m pip install playwright`、`python -m playwright install chromium`。对已应用 001 至 003 的专用 MySQL 测试库设置 `AGENTOS_TEST_MYSQL=1`，再执行 `python -m pytest tests/integration tests/acceptance`。本次开发未执行这些测试或数据库迁移。
